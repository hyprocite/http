## Answer（原答、批注与参考回答）

### 1. `shared_ptr` 的引用计数如何工作？

**原答：**

> 引用计数使用控制块控制指针的创建与销毁，其中控制块中的计数count 为一个共享裸指针，在构造函数中被赋值给每一个指向这个对象的share ptr ，在析构函数中进行减法计数，当计数为0时销毁指向的变量，控制块在作用域内仍会保留

**批注：需要纠正控制块和计数的含义。**

- 控制块保存强引用计数、弱引用管理信息和删除器等；计数不是“共享裸指针”。共享所有权的智能指针关联同一个控制块。
- 复制 `shared_ptr` 增加强引用计数；销毁或 `reset()` 会释放一份强引用。移动只转移这一份所有权，通常不改变该所有权组的强引用计数；移动赋值还可能释放目标原先持有的对象。
- 强引用计数归零时，调用删除器销毁所管理的对象。控制块是否继续存在，取决于是否还有 `weak_ptr` 等需要它，不取决于原来创建对象的作用域。
- 不要分别用同一个裸指针构造两个独立的 `shared_ptr`：它们会形成不同控制块，可能重复释放对象。

**参考回答：**

`shared_ptr` 通过控制块管理共享所有权。复制共享指针会增加强引用计数，销毁或重置会减少计数；最后一份强引用释放时，对象被销毁。如果还有 `weak_ptr`，控制块会继续存在，用于判断对象是否过期；弱引用也全部释放后，控制块才能释放。

### 2. `weak_ptr` 为什么不增加强引用计数？

**原答：**

> weak_ptr意在观察指针对象若，其出现是为了解决循环引用导致的对象无法销毁的问题

**批注：方向正确，需要补充“不拥有对象”和 `lock()`。**

`weak_ptr` 是非拥有的观察者，不延长对象寿命，因此不增加强引用计数，但会参与控制块的弱引用管理。循环引用是它的重要应用场景之一。访问对象前应调用 `lock()`：对象仍存活时得到共享所有权并增加强引用计数；否则得到空 `shared_ptr`。

**参考回答：**

`weak_ptr` 观察某个共享所有权组，但不拥有对象，因此不会阻止强引用计数归零。它可以打破相互持有 `shared_ptr` 形成的循环引用。使用对象时通过 `lock()` 获取临时 `shared_ptr`，成功后保证对象在使用期间存活。

### 3. `shared_from_this()` 为什么不能随意在构造函数中使用？

**原答：**

> shared_from_this 需要在控制块已经创建之后，将对象内部share指针指向外部创建的控制块

**批注：关键是共享所有权关联已建立，而不只是控制块已创建。**

`enable_shared_from_this` 内部维护的是弱引用。通过 `make_shared` 或合适的 `shared_ptr` 构造方式接管对象时，会建立这个弱引用与共享所有权组的关联。对象执行构造函数时，这个关联通常尚未建立；即使 `make_shared` 已分配控制块，也不能据此在构造函数内调用 `shared_from_this()`。未建立关联时调用会抛出 `std::bad_weak_ptr`（C++17 及以后）。

**参考回答：**

`shared_from_this()` 利用内部弱引用获取与现有 `shared_ptr` 共用控制块的共享指针。它要求对象已经被正确接管，并完成共享所有权关联，所以通常不能在构造函数内调用。本项目先 `make_shared<Connection>()`，再调用 `start()`，此时才能安全地用 `shared_from_this()` 捕获自身。不能用 `shared_ptr<Connection>(this)` 替代，否则可能产生独立控制块并重复释放。

### 4. epoll LT 和 ET 有什么区别？

**原答：**

> LT和ET分别为水平触发和边缘触发， 后者需要搭配菲阻塞fd使用，因为若是阻塞fd在，边缘触发只通知一次的特性会导致响应在fd被阻塞的时候无法得到及时处理

**批注：名称正确，需要纠正“只通知一次”和阻塞的原因。**

- LT 是默认模式：只要 fd 仍满足监听的就绪条件，后续 `epoll_wait()` 仍可返回它。
- ET 通过 `EPOLLET` 启用：通常在就绪状态发生变化时通知，不能依赖未处理完的数据持续触发通知；不是说一个连接只通知一次。
- ET 的常用处理方式是非阻塞 I/O，并在一次通知后持续读取，直到 `EAGAIN/EWOULDBLOCK`，或遇到 EOF、错误。否则数据可能留在内核缓冲区里，却没有新的通知促使应用继续读取。
- 若对阻塞 fd 持续读取，读完现有数据后，下一次 `recv()` 可能阻塞整个事件循环，其他连接也无法及时处理。LT 模式下的单线程 Reactor 同样通常需要非阻塞 I/O。

**参考回答：**

LT 在 fd 持续就绪时可反复通知，ET 主要在就绪状态变化时通知。ET 通常配合非阻塞 fd，收到可读通知后循环读取到 `EAGAIN`，避免遗漏剩余数据，同时避免阻塞事件循环。当前项目没有设置 `EPOLLET`，使用的是 LT；虽然如此，读取逻辑也采用非阻塞循环读取。

### 5. Reactor 模式如何工作？

**原答：未作答。**

**批注：需要串起监听、等待、分发与实际 I/O。**

**参考回答：**

Reactor 将 fd 的就绪事件与业务处理器关联起来。事件循环通过 `epoll_wait()` 等待就绪事件，返回后根据 fd 找到回调并执行；回调再进行非阻塞读写和业务处理。epoll 通知的是“可以尝试 I/O”，实际 `recv()`、`send()` 仍由应用执行。

本项目监听 fd 的回调执行 `accept()`，创建 Connection 并注册客户端 fd 的回调。客户端事件到来后，经 `on_event()` 分发到读写处理，再进行 HTTP 解析、路由和响应发送。多个事件由当前线程依次处理，因此回调中应避免长时间阻塞。

补充：`add_fd()`、`mod_fd()`、`del_fd()` 都立即调用 `epoll_ctl()`，没有加入待执行任务队列。`callbacks_` 是回调映射表；`epoll_wait()` 返回一批就绪事件，loop 处理每个事件时再查找回调。事件不保证按发生时间严格排序。

### 6. 客户端关闭连接时，你的 HTTP Server 如何释放资源？

**原答：**

> 客户端关闭连接的时候， epoll发出EPOLLRDHUP事件，而后进入connetion的on_event分支， 优先让on_readable 去读EOF，这样可以同时检查有无未处理的消息同时走on_readable流程处理关闭，不需要创建新的分支

**批注：读到 EOF 的思路正确，但还缺少资源释放和对象生命周期。**

- 正常关闭可能表现为 `EPOLLIN`、`EPOLLRDHUP` 等事件的组合，不能假定只有 `EPOLLRDHUP`。`EPOLLRDHUP` 也可能表示对端只关闭发送方向。
- `recv()` 先处理剩余字节，返回 `0` 才表示读到 EOF；如果还有输出数据，当前代码会等待发送完成再关闭。
- 客户端关闭不会自动关闭服务器持有的 socket fd，服务器需要主动注销事件、关闭 fd、移除业务状态和共享持有者。

**参考回答：**

客户端正常关闭发送方向后，epoll 通知相关事件，`on_event()` 调用 `on_readable()` 读取剩余数据。`recv()` 返回 `0` 时设置 `read_eof_`；如果没有待发送数据，立即调用 `close()`，否则等待 `flush_output()` 发送完后调用 `close()`。

在正常单线程路径且注销成功的情况下，清理顺序如下：

1. `closed_ = true`，防止重复关闭，并阻止后续读写。
2. `del_fd()` 同步执行 `epoll_ctl(DEL)`，并从 `callbacks_` 移除事件回调，释放该回调捕获的一份共享所有权。
3. 将 `fd_` 置为 `-1`，调用 `::close(old_fd)` 关闭 socket；析构时因 `fd_ == -1` 不会再次关闭它。
4. 清空输入、输出缓冲区，重置输出偏移。
5. 调用关闭回调：先从 `ChatServer::parsers_` 删除解析器，再通过关闭钩子从 `main::connections` 移除连接。
6. 当前事件处理返回后，`run()` 的局部回调副本释放其捕获的 `self`；没有其他强引用时，Connection 析构。

这里删除回调表记录不会中断当前回调：`run()` 在调用前已复制回调到局部 `cb`，该副本仍持有 Connection。`close()` 中调用关闭回调时也有局部 `self` 保活。

Connection 的长期持有者是 `main::connections` 和 EventLoop 回调捕获的 `self`。ChatServer 不长期持有 Connection，`parsers_` 的裸指针键也不保活；正常关闭时会在对象销毁前删除这个键，遗漏清理则可能残留悬空地址，并在地址复用后误用旧解析器。

**当前实现的边界：** `epoll_ctl(DEL)` 失败时，`del_fd()` 会提前返回，未删除 `callbacks_`；而 `close()` 忽略返回值，仍会关闭 fd。因此上述完整释放流程依赖注销成功，失败分支存在回调和对象残留的问题。另外，服务器退出前应主动关闭存量连接，避免回调表销毁过程中触发 Connection 析构，再反过来访问回调表。

**补充：** 一次请求处理完成不一定关闭连接。非 keep-alive 请求通过 `send(response, true)` 在响应发送完后关闭；keep-alive 连接继续等待后续请求。客户端突然断电或网络中断也不一定立即产生关闭通知，需要超时、心跳或 TCP keepalive 等机制检测。
